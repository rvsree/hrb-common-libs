# hrb-common-libs Roadmap

Phase-by-phase plan and history, same convention as `hrb_chatbot_v2`'s `docs/agent-reference/RAG-ROADMAP.md`. A phase gets a `**Spec:**` block written before its code starts (`/spec-new`), and its checkbox flips to `- [x]` once implemented and verified.

**Scope correction, found while starting Phase 2 (2026-10-21):** `common/clients/db_client/` in `hrb_chatbot_v2` isn't just Postgres - it also holds vector-store clients (Chroma/Pinecone) with no extra of their own, and 13 feature-specific business stores (interview Q&A, conversation memory, HITL, CI/CD, ...) that must never be extracted into a shared library - that's exactly the business-logic-leak the Common-Libs Connectors doc already warned against. Corrected: added an 11th extra, `vectorstore`; narrowed `db` to a generic connection manager (new code, not a literal port - nothing purely generic existed to port); excluded every `*_store.py` file - those stay in whichever service owns them when that service is actually built.

- [x] **Phase 16 (done) — Wire retry/circuit-breaker into every real outbound client.** 79/79 tests pass (6 new: retry-then-succeed + circuit-breaker-trips-after-2-failures for `openai_client.py`, `chroma_client.py`, `db/connection.py` - representative, not every one of the 7 files re-proven individually, same composition pattern applied mechanically everywhere else, confirmed via a structural grep: 8 `CircuitBreaker` instances, 20 `@with_retry()` call sites, matching every `log_backend_call` site that existed before this phase). `bandit -r src/hrb_common -ll` clean. MUST #2/#3 from the NFR spec are now actually true, not just "the tool exists somewhere" - verified by re-reading every touched file after editing, not assumed from the diff.
  - **Spec:**
    - **Context:** `hrb_chatbot_service`'s `docs/dev-reference/nfr-platform-components/spec.html` MUST #2/#3 require "every outbound call to Postgres, the vector store, an LLM provider, or another service goes through a retry/backoff wrapper" and a circuit breaker. A 2026-10-22 audit (prompted by the user, who specifically asked for an audit rather than trusting a first-pass summary) found `with_retry()`/`CircuitBreaker` (Phase 1) are correctly built and tested as standalone primitives, but applied in exactly one place in the whole repo - `mcp/client.py`. Every real Postgres/vectorstore/LLM client (`db/connection.py`, `chroma_client.py`, `pinecone_client.py`, `openai_client.py`, `anthropic_client.py`, `bedrock_client.py`, `open_router_client.py`) has zero usage, confirmed via direct grep, not assumed. The spec's own MUST isn't met today - this phase closes that gap. User-directed: this was the first of 3 identified gaps (request_id middleware/log-wiring, Secrets Manager SDK are the other 2, explicitly deferred - not this phase's scope) and the one the user picked to prioritize.
    - **Data/API contracts:** none - every wrapped method keeps its exact existing signature and return type. A circuit-open or retry-exhausted failure surfaces as the same exception type each client's own `health_check()`/caller already catches (`CircuitOpenError` is new and NOT silently swallowed - a caller that doesn't already catch a broad `Exception` around these calls will see a new exception type, called out explicitly in Out of scope below since updating every consuming service's own exception handling isn't this phase's job).
    - **Composition order (the one real design decision):** circuit breaker is the OUTER wrapper, retry is the INNER one - `with self._circuit_breaker: <retry-decorated call>`. Reasoning: the breaker should be consulted once per logical call (fail fast via `CircuitOpenError` without even attempting a retry loop against a backend already known to be down) and should count ONE consecutive failure per logical call even if that call internally retried 3 times - not 3 failures for 1 real outage. Pattern used at every call site: a small local closure decorated with `@with_retry()`, called inside the existing `with self.<lock>, self._circuit_breaker, log_backend_call(...):` block (adding `self._circuit_breaker` into that same `with` alongside whatever's already there, e.g. `self.collection_lock`) - not a new nesting level, not a new helper module (every call site is already inside exactly one `with` statement today; this adds one more context manager to that same statement).
    - **Source:** each client class's `__init__` gains `self._circuit_breaker = CircuitBreaker(name="<provider>")` (one instance per client instance, so consecutive-failure state persists correctly across calls on that instance - never a fresh `CircuitBreaker()` per call, which would always read as "never tripped"). Every method that currently has a `log_backend_call(...)` block gets its real backend call wrapped in a `@with_retry()`-decorated local closure, called inside that same `with` block alongside the new `self._circuit_breaker`. `db/connection.py::get_connection()` (a plain function, not a class method, no existing `log_backend_call`) gets the same closure-plus-`with_retry` pattern but no circuit breaker instance of its own to persist across calls (it's a free function with no `self` - a module-level `_connection_circuit_breaker = CircuitBreaker(name="postgres")` singleton, same reasoning as a class's own `self._circuit_breaker`, just module-scoped since there's no instance to hang it off).
    - **Files/methods in scope:** `db/connection.py` (`get_connection`), `vectorstore/chroma_client.py` (`upsert`/`query`/`delete`/`update_metadata`/`get_all_chunks`), `vectorstore/pinecone_client.py` (same 5 methods), `llm/openai_client.py` (`OpenAIChatClient.ask`/`ask_with_tools`, `OpenAIEmbeddingClient.get_embeddings`), `llm/anthropic_client.py` (`ask`/`ask_with_tools`), `llm/bedrock_client.py` (`ask`/`ask_with_tools`), `llm/open_router_client.py` (`ask`/`ask_with_tools`). `health_check()` methods are explicitly NOT wrapped - a health check's whole job is to report real-time backend status including failure, and a tripped circuit breaker would make a down backend's health check itself raise instead of reporting `{"status": "unhealthy", ...}` as designed.
    - **User-visible behavior:** a transient failure (one dropped connection, one rate-limit blip) now retries automatically (3 attempts, exponential backoff from 0.5s) instead of failing the whole request on the first hiccup. A backend that's genuinely down now fails fast with a clean `CircuitOpenError` after 2 consecutive real failures, for the next 10s, instead of every subsequent call separately waiting out its own full retry/timeout cycle against a backend already known to be unreachable.
    - **Failure modes:** `CircuitOpenError` (new) when the breaker is tripped - a `RuntimeError` subclass, so any caller catching broad `Exception`/`RuntimeError` already handles it; one that catches a narrower provider-specific exception type will now also need to catch this, flagged as a real downstream consideration, not fixed here (no consuming service - `hrb_chatbot_service` itself doesn't even depend on this package yet, per the earlier audit's own finding that these extras are built but not yet consumed by a real service). A retry-exhausted call still raises the real underlying exception (`reraise=True` on `with_retry`, unchanged from Phase 1), not a new wrapped type.
    - **Out of scope:** `langchain_vector_store.py` - confirmed by reading it directly: it builds LangChain's own `Chroma`/`PineconeVectorStore` objects that call the raw `chromadb`/`pinecone` SDKs directly, bypassing `ChromaDBClient`/`PineconeClient`'s own wrapped methods entirely - retry/circuit-breaker protection for that path would need to live in whichever consuming service's own retrieval code calls `store.similarity_search(...)`, not here; flagged, not silently left unprotected without explanation. The other 2 audit gaps (request_id middleware/log wiring, real Secrets Manager SDK call) - explicitly deferred to their own later phases, user-prioritized this one first. Updating `mcp/client.py`'s own already-correct usage - untouched, it's the one place this pattern already exists correctly.
    - **Open questions:** none blocking - the composition-order design decision is stated above, not left open.

- [x] **Phase 17 (done) — Real Secrets Manager SDK call + request_id middleware/log-wiring, the other 2 gaps from Phase 16's own audit.**
  - **Spec:**
    - **Context:** `hrb_chatbot_service`'s `docs/dev-reference/nfr-platform-components/spec.html` audit (2026-10-22) found 3 real gaps; Phase 16 closed the retry/circuit-breaker one. User-directed, same day: close the other 2 now, before Gateway's real AWS provisioning.
    - **Part A - Secrets Manager:** MUST #4 says every secret "resolves through one settings helper backed by Secrets Manager/env." `read_secret()` (Phase 1) already has the right interface and precedence shape (`passed_in_value -> env -> default`) but never calls the real AWS SDK. New precedence: `passed_in_value -> env -> AWS Secrets Manager (best-effort, cached) -> default`. Env stays checked *before* Secrets Manager deliberately - in this project's own real deployed architecture, App Runner's `RuntimeEnvironmentSecrets` already resolves Secrets-Manager-backed values INTO plain env vars at container start (confirmed directly via `aws apprunner describe-service` against the real `hrb-chatbot` production service earlier this session - `POSTGRES_DB_PASSWORD`/`OPENAI_API_KEY`/etc. are all real Secrets-Manager-backed secrets, injected as env vars, never fetched by application code directly) - so env is the fast, already-proven path for every service deployed that way; a direct SDK call is the fallback for contexts where it isn't pre-populated (local dev with AWS credentials configured, or a future service that reads Secrets Manager directly instead of via App Runner's injection).
    - **Source (Part A):** `observability/secrets.py` gains a module-level cache (`_secrets_manager_cache: dict[str, str | None]`, keyed by secret id, populated once per process - a real AWS API call on every single settings read would be a real latency/cost problem, and secret values don't need to be re-fetched mid-process the same way App Runner's own injection is fixed at container start too) and a new `_fetch_from_secrets_manager(key)` helper using `boto3.client("secretsmanager")` (top-level `import boto3`, matching this repo's own existing convention in `s3_client.py`/`ses_client.py`/`bedrock_client.py` - not a lazy/conditional import) + `get_secret_value(SecretId=key)`, wrapped in a broad `try/except Exception` that returns `None` on any failure (no credentials configured, secret doesn't exist, network error) - never raises, same "a down/unreachable/unconfigured backend degrades to the next fallback, never breaks the caller" convention every other client in this repo already follows. `boto3==1.43.89` added to the `observability` extra's own `pyproject.toml` dependency list (matching the exact pinned version `llm`/`storage`/`email` already use) - a real, deliberate dependency-footprint increase for the one extra every other extra already depends on, flagged here rather than silently added; accepted given this project's own AWS-centric architecture means most real consuming services end up depending on `boto3` through some other extra anyway.
    - **Part B - request_id middleware + log wiring:** MUST #1 + the spec's own acceptance criterion ("a new service that imports `hrb_common_libs[observability]` gets request_id propagation and structured logging with zero additional code beyond calling the provided middleware/decorator") - today, `request_context.py`'s contextvar plumbing exists but nothing calls it automatically, and `get_logger()`'s own format string has no request_id placeholder at all (confirmed by reading both files directly, not assumed). This is the first custom `BaseHTTPMiddleware` anywhere in this whole ecosystem - every existing middleware (`hrb_chatbot_service`'s CORS, `hrb_api_gateway_service`'s `configure_cors()`) uses FastAPI's own built-in `CORSMiddleware`, not a hand-written one.
    - **Source (Part B):** new `observability/request_id_middleware.py::RequestIdMiddleware(BaseHTTPMiddleware)` - `dispatch()` reads an incoming `X-Request-ID` header if present (so a caller, or an upstream Gateway, can propagate its own id through), else generates one via the existing `new_request_id()`; calls `set_request_id()`; echoes the id back on the response via the same header (so a client can correlate its own call with server-side logs without needing to parse them). `logger.py` gains a `_RequestIdFilter(logging.Filter)` that sets `record.request_id = get_request_id() or "-"` on every record, added via `handler.addFilter(...)` inside `get_logger()`; `LOG_FORMAT` gains a `[%(request_id)s]` segment. `call_logger.py` needs **no change** - a design decision made then reverted during implementation: adding `request_id` to its own `extra={...}` dict too would be pure redundancy, since `logger.py`'s own filter already stamps every record from any `get_logger()`-created logger (including `log_backend_call()`'s), overwriting any `extra` value with the same one regardless. **`RequestIdMiddleware` is reached via its own submodule path (`from hrb_common.observability.request_id_middleware import RequestIdMiddleware`), not re-exported from `observability/__init__.py`** - a design decision found necessary during implementation, not in the original plan: `starlette` isn't a declared dependency of the `observability` extra, so eagerly importing the middleware in `__init__.py` would force every consumer of ANY `observability` symbol (`get_logger`/`with_retry`/`CircuitBreaker`/`read_secret`) to also have `starlette` importable, violating this same spec's own "a service with no DB access still gets retry/circuit-breaker/logging for free" constraint for non-web consumers.
    - **User-visible behavior:** a service that does `app.add_middleware(RequestIdMiddleware)` (one line) gets every log line for a request automatically tagged, with zero other code changes - matches the spec's own acceptance criterion exactly, not approximately. `read_secret()`'s own call sites (every extra) are unchanged - same function signature, just a richer fallback chain.
    - **Failure modes:** Secrets Manager unreachable/unconfigured/secret-not-found all degrade silently to the next tier (env already failed by the time this runs, so falls through to `default`) - never raises, never blocks app startup. No `X-Request-ID` header on an incoming request is not an error - a fresh id is generated, same as today's "no request_id set yet" behavior for a background job (per `request_context.py`'s own existing docstring).
